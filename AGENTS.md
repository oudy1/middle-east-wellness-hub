- Keep volunteer response reads in the admin-authenticated `volunteer-sheet` Edge Function (Google Sheets credentials stay server-side), or from a CSV export the admin opens on `/admin/volunteers`, parsed in the browser only and never uploaded or stored, so volunteer details never land in the database.
- Public-submission tables accept anonymous inserts only through RLS policies with explicit length/format checks (never `WITH CHECK (true)`); intake tables no site form uses stay closed to the public, so they cannot be flooded.
- Public forms that send email (Contact, topic requests) pass `useSpamGuard` fields (hidden trap + fill time) to `send-contact-email`, which silently drops bot hits, applies a best-effort per-IP limit, and never returns provider error details to the browser.
- Admin access is granted only by the `grant_allowlisted_admin` trigger when a confirmed sign-in email matches the service-only `admin_email_allowlist`; add admins by inserting into that list, never from client code.
- Every event is one record in `content/events.json` read through `src/lib/events.ts` (homepage, Programs, Recordings, news, search, chatbot, approved links); its phase comes from the Toronto calendar date plus confirmed facts: after the date it shows "Registration closed" until `heldConfirmed`, a published recording or a recap is added, registration links appear only while upcoming, and the public .ics files must equal their builders (tested), so no page shows a past event as upcoming, an old sign-up link, or claims an event happened just because its date passed.
- Events, recordings (`content/webinars.json`) and studies (`content/studies.json`) carry a `status` from `src/lib/contentStatus.ts`; only `published` items reach visitors, and `contentRecords.test.ts` fails on a published item missing Arabic text, an unknown poster key or a broken recording link, so drafts and half-translated content cannot ship.
- Every internal link the chatbot, its knowledge index or the header search can produce must be listed in `content/chatbot-routes.json` (mirrored in the `shams-chat` function); `chatbotSearch.test.ts` fails on any unlisted address, so invented or dead anchors cannot ship.
- Time-limited chatbot knowledge entries carry `activeUntil` (Toronto date) from the event's own module, so the assistant stops recommending an event after it ends.
- Site search and chatbot retrieval share `src/lib/searchText.ts` (Arabic normalization, length-based typos, prefix match) and the header/home finder uses `searchSite` in `src/lib/siteSearch.ts` (curated list + knowledge index, ranked by matched words), so both stay in step without a search server or paid service.
- Translations run on i18next (`src/i18n/index.ts`) behind the existing `useLanguage().t`, with flat keys in `content/translations/*.json` (keySeparator off); counts use `t(key, { count })` with `_one/_other` (+ Arabic `_zero/_two/_few/_many`), and `translations.test.ts` fails on missing Arabic text, missing plural forms or unknown keys, so gaps are caught before publishing.
- The language menu lists only `AVAILABLE_LANGUAGES` (languages with every English key translated), and a saved hidden language falls back to English, so half-translated languages never reach visitors and reappear on their own once complete.
- Every page except the homepage is loaded with `lazyWithRetry` in `App.tsx`, lower homepage sections sit inside `LazySection` (render when scrolled near, or at once when the URL has a #hash), and the chat window loads on first open (idle/hover warm-ups go through `preloadQuietly`, so a file removed by publishing never logs an error); `tests/e2e/lazy-loading.spec.ts` guards this, so phones download only what they view and a stale file after publishing reloads once instead of breaking.
- Doctor listings are public only when `status = 'published'` (RLS); the `healthcare_workers_guard` trigger blocks visitors from setting any review field and moves applicant email/notes into admin-only `healthcare_worker_reviews`, `healthcare_workers_log` records history, and a partial unique index stops duplicate published listings, so unreviewed or private details never reach visitors (check: `supabase/tests/healthcare_worker_approval.sql`, `tests/e2e/directory-approval.spec.ts`).
- The public SHAMS team lives only in `content/team.json` (read through `src/lib/team.ts` by the About page, site search and chatbot knowledge); it holds names, team affiliations and confirmed titles only, former members go to the never-loaded `content/team-archive.json`, and `team.test.ts` pins the approved roster, so one edit updates every place and private details never ship.
- Affiliated researchers live only in `content/researchers.json` (read through `src/lib/researchers.ts` by the Research page, site search and chatbot knowledge, one entry each), separate from the team, and `researchers.test.ts` checks Arabic text and that names are findable, so one edit updates every place.
- The Services "How Can We Help You?" guide (`src/lib/helpNavigator.ts`) links only to route keys in `content/chatbot-routes.json` or official ontario.ca/canada.ca pages, checked by `helpNavigator.test.ts`, so it can never point at an invented or unofficial page.
- Listing cards use the shared `Card` base plus `.card-interactive` (index.css), links styled as buttons use `Button asChild` (never a Button inside a link), poster sliders use `ui/carousel` inside a `dir="ltr"` wrapper with language-ordered slides, 44px arrows/dots and a tap-to-enlarge dialog, and header menus keep `role="menu"` with arrow-key focus (`tests/e2e/header-dropdown.spec.ts`, `poster-carousels.spec.ts`), so cards, posters and menus look and behave the same in English and Arabic without a new UI library.
- The chat answers simple questions and every safety message (crisis, urgent symptoms, doses) in the browser through `src/lib/chatInstantAnswers.ts` before calling the AI, shows at most two action buttons with their sources, turns outside links into buttons only when `src/lib/approvedExternalLinks.ts` allows them (official domains, links already on the site, registration links until the event ends), and falls back to matching verified pages when the AI fails; `chatInstantAnswers.test.ts` and `tests/e2e/chatbot-navigation.spec.ts` (fake AI) guard this, so common questions cost nothing, work offline and can never open an invented or expired link.
- Mentor/mentee form links live only in `src/lib/programLinks.ts` (tested with sitemap coverage), so one edit updates every page.
